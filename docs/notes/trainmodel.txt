# 3. Why do we split by `trip_id`?

This is **one of the most important parts of the code.**

Suppose T001 has:

| trip_id | days_left | occupancy |
| ------- | --------: | --------: |
| T001    |        20 |       30% |
| T001    |        15 |       45% |
| T001    |        10 |       60% |
| T001    |         5 |       80% |

If you randomly split rows:

```text
TRAIN:
T001 → 20 days
T001 → 15 days

TEST:
T001 → 10 days
T001 → 5 days
```

The model has already seen T001 during training.

That's not a proper test.

So instead:

```text
TRAIN
T001
T002
T003
T004
...

TEST
T100
T101
T102
...
```

**Every snapshot belonging to one trip stays together.**

---

# 6. Now separate Features and Target

You have:

```python
NON_FEATURE_COLS = [
    "trip_id",
    "route",
    "final_occupancy_pct"
]
```

Why remove these?

### `trip_id`

It's just an identifier.

The model shouldn't learn:

```text
T001 → high demand
T002 → low demand
```

### `route`

Your code removes the raw route string because ML models can't directly use:

```text
Mumbai → Pune
```

You are instead using engineered information such as:

```text
route_avg_occupancy_loo
```

### `final_occupancy_pct`

This is the **answer**.

It cannot be given to the model as an input.

Otherwise:

```text
Model input = final occupancy
Model output = final occupancy
```

That would be cheating/data leakage.

# 8. Why train 3 different models?

You don't know beforehand which model will work best.

So you test:

### Model 1 — Linear Regression

```text
Simple baseline
```

It asks:

> Can the relationship between features and final occupancy be approximated using mostly straight-line relationships?

---

### Model 2 — Random Forest

Random Forest creates many decision trees.

Conceptually:

```text
Tree 1 ─┐
Tree 2 ─┤
Tree 3 ─┤
Tree 4 ─┤ → Average prediction
...     │
Tree 300┘
```

It can capture nonlinear relationships.

For example:

```text
If days_left < 7
AND current occupancy > 70%
AND route popularity = high
→ very high final occupancy
```

---

### Model 3 — XGBoost

XGBoost builds trees sequentially.

Conceptually:

```text
Tree 1
  ↓
Find mistakes
  ↓
Tree 2 fixes mistakes
  ↓
Tree 3 fixes remaining mistakes
  ↓
...
  ↓
Final prediction
```

It's often very strong for tabular datasets like yours.

# 12. Now comes evaluation

This function:

```python
evaluate(...)
```

calculates three metrics.

---

## MAE

Mean Absolute Error.

Suppose:

| Actual | Predicted |
| -----: | --------: |
|     90 |        86 |
|     80 |        84 |
|     70 |        72 |

Errors:

```text
4
4
2
```

Average:

[
MAE = \frac{4+4+2}{3}=3.33
]

So:

> The model is off by about **3.33 percentage points on average**.

**Lower MAE = better.**

---

# 13. RMSE

RMSE penalizes large mistakes more heavily.

For example:

```text
Actual = 90
Prediction = 60
```

is a much bigger problem than:

```text
Actual = 90
Prediction = 87
```

So RMSE is useful for detecting big prediction errors.

**Lower RMSE = better.**

---

# 14. R²

R² tells you roughly:

> How much of the variation in the target is explained by the model.

For example:

```text
R² = 0.90
```

means the model explains about 90% of the variation in the target under this evaluation setup.

**Higher R² = better.**

# 16. What is `error_by_days_left_bucket()`?

This is a particularly nice part of your project.

You don't just ask:

> "How accurate is the model?"

You also ask:

> **"How accurate is the model at different points before departure?"**

You create buckets:

```text
0–3 days
4–7 days
8–15 days
16–30 days
30+ days
```

For example:

| Days left |  MAE |
| --------- | ---: |
| 30+       | 10.2 |
| 16–30     |  7.4 |
| 8–15      |  5.1 |
| 4–7       |  3.2 |
| 0–3       |  1.8 |

That makes intuitive sense.

### Why?

30 days before departure:

```text
Very little booking history
       ↓
More uncertainty
       ↓
Larger error
```

3 days before departure:

```text
Lots of booking history
       ↓
Much clearer demand pattern
       ↓
Smaller error
```

This is a **great business insight**.
