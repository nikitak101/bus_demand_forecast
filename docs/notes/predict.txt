Imagine a bus company asks:

> "I have a Mumbai → Pune AC Sleeper bus. It has 32 seats. It's 10 days before departure and 18 seats are already booked. How full will this bus probably be when it leaves?"

You give the system:

```python

    "bus_type": "AC Sleeper",
```

The system converts this information into the **same features that XGBoost saw during training**.



The code explicitly says it does not retrain or modify Bronze/Silver/training data. 

So:

### `finalize_model.py`

```text

   ↓

model_xgboost_final.pkl
```

### `predict.py`

```text

   ↓

```

# 4. Step 1 — Load the trained model

This part:

```python
def _load_artifacts():
    with open(MODEL_PATH, "rb") as f:
        model = pickle.load(f)

    with open(FEATURE_COLUMNS_PATH) as f:
        feature_cols = json.load(f)

    with open(ROUTE_LOOKUP_PATH) as f:
        route_lookup = json.load(f)
```

loads **three things**:

| File                      | Purpose                                |
| ------------------------- | -------------------------------------- |

| `feature_columns.json`    | Exact features/order expected by model |
| `route_avg_lookup.json`   | Historical route occupancy averages    |

So think:

```text

feature_columns.json
        ↓
"What features/order should I give you?"

route_avg_lookup.json
        ↓

```

The uploaded code loads exactly these three artifacts.

# 6. Step 3 — Calculate time features

From the dates, the code calculates:

```python
booking_window_days = departure_date - booking_open_date
```

Here:

```text
Aug 30 - Aug 10
= 20 days
```

Then:

```python
days_since_open = as_of_date - booking_open_date
```

```text
Aug 20 - Aug 10
= 10 days
```

And:

```python
days_left = departure_date - as_of_date
```

```text
Aug 30 - Aug 20
= 10 days
```

So:

| Feature             |       Value |
| ------------------- | ----------: |
| booking_window_days |          20 |
| days_since_open     |          10 |
| days_left           |          10 |
| days_left_ratio     | 10/20 = 0.5 |

These are important because **the same 18 bookings mean something different 1 day before departure vs 30 days before departure.**

# 7. Step 4 — Calculate current occupancy

The code:

```python
current_occupancy_pct = 100 * current_seats_booked / capacity
```

For our example:

```text
18 / 32 × 100
= 56.25%
```

It also calculates:

```python
seats_remaining = capacity - current_seats_booked
```

So:

```text
32 - 18 = 14 seats remaining
```

Therefore:

```text
Current occupancy = 56.25%
Seats remaining = 14
```

# 8. Step 5 — Calculate booking velocity

This is one of the most important features.

Suppose the user doesn't provide previous booking history.

The code estimates:

```python
avg_daily_rate =
current_seats_booked / days_since_open
```

Here:

```text
18 / 10
= 1.8 seats/day
```

Then it estimates:

```text
1 day ago:
18 - 1.8 = 16.2

3 days ago:
18 - (1.8 × 3)
= 12.6

7 days ago:
18 - (1.8 × 7)
= 5.4
```

Then:

```python
booking_velocity_3d =
(current - seats_3d_ago) / 3
```

Approximately:

```text
(18 - 12.6) / 3
= 1.8 seats/day
```

And:

```python
booking_velocity_7d =
(current - seats_7d_ago) / 7
```

Approximately:

```text
(18 - 5.4) / 7
= 1.8 seats/day
```

So the model learns:

> "This bus is currently gaining approximately 1.8 bookings/day."

The file distinguishes between **real history provided by the caller** and **estimated history**.

# 9. What if we actually know the booking history?

This is better.

Instead of:

```python
current_seats_booked=18
```

only, you could provide:

```python
recent_seats_booked={
    "-1": 17,
    "-3": 14,
    "-7": 8
}
```

Meaning:

```text
Today       = 18
1 day ago   = 17
3 days ago  = 14
7 days ago  = 8
```

Then:

```text
3-day velocity
= (18 - 14) / 3
= 1.33 seats/day
```

and:

```text
7-day velocity
= (18 - 8) / 7
= 1.43 seats/day
```

This is **better than estimation** because you're giving the model actual booking behavior.

# 12. What happens with an unknown route?

Suppose user enters:

```text

```

but that route wasn't present in the reference data.

The code doesn't crash immediately.

It does:

```text

```

and uses a fallback distance.

It also uses the global average occupancy if there is no historical route average.  

And importantly:

```text
WARNING:
No historical data for route...
using global average occupancy
```

So the system is telling you:

> "I can still predict, but this prediction is less reliable because I don't know this route historically."

That's good production behavior.

# 15. Step 9 — Exact feature order

This part is VERY important:

```python
ordered = {c: row[c] for c in feature_cols}
```

Why?

Suppose during training XGBoost saw:

```text
Feature 1 = days_left
Feature 2 = capacity
Feature 3 = price
Feature 4 = occupancy
```

But during prediction you accidentally send:

```text
Feature 1 = price
Feature 2 = occupancy
Feature 3 = days_left
Feature 4 = capacity
```

The numbers are present, but the model interprets them incorrectly.

So:

```text
Training:
[A, B, C, D]

Prediction must be:
[A, B, C, D]
```

NOT:

```text
[B, D, A, C]
```

That's why `feature_columns.json` exists.

The source explicitly describes exact feature formulas **and exact column order** as critical to avoiding training/serving skew.
